## Web 기본

### 관련 용어 정리

웹 서버(Web Server) : 정보를 제공하는 주체

웹 클라이언트(Web Client) : 정보를 받는 고객

프론트엔드(Front-end) : 클라이언트에게 요청을 받는 부분

백엔드(Back-end) : 클라이언트의 요청을 처리하는 부분

웹 리소스(Web Resource) : 페이지가 보여주고 있는 정보(글, 폰트, 배경, 이미지 등등), 모든 웹 리소스는 고유의 URL을 가지고 있다.
`https://dreamhack.io/index.html` → `dreamhack.io`에 있는 `index.html`을 가져와라는 뜻

![](/assets/img/Xpert(4)/01.png)

HTML(HyperText Markup Language) : 태그와 속성을 통한 구조화된 문서 작성을 지원

CSS(Cascading Style Sheets) : 웹 리소스들을 시각화 방법을 기재한 스타일 시트

JS(JavaScript) : 웹 문서의 동작을 정의

### 웹 클라이언트, 서버 사이의 통신

1. 클라이언트 접속, 서버에 HTTP 형식 리소스를 요청한다.
2. 서버에서 처리 이후 HTTP 리소스를 전달한다.
3. 클라이언트의 브라우저에서 서버에게 응답 받은 웹 리소스를 보여준다.

## HTTP(Hyper Text Transfer Protocol)

클라이언트의 Request와 서버의 Response 형식으로 정의한 프로토콜(HTTP 80번, HTTPS 443번 사용)

### HTTP의 구조

![](/assets/img/Xpert(4)/02.png)

#### HTTP Header

각 줄은 CRLF( 줄 바꿈을 나타내는 제어 문자열 )로 구분된다.
필드와 값으로 구성되며 HTTP의 메시지 속성, HTTP 바디의 속성을 나타낸다.

#### HTTP Body

빈 줄 뒤에 나타나며 클라이언트나 서버에 전송하는 데이터를 담고 있다.

#### HTTP 요청

서버에게 특정 동작을 요구하는 메시지

1. HTTP 요청의 시작 줄은 Method, Target, ver로 구성된다.
2. HTTP 표준에서 정의하는 메소드는 8개가 있다. (ex. GET, POST 등등)

GET : 리소스를 가져와달라고 요청하는 메소드

POST : 요청 대상에게 데이터를 보내는 메소드, 데이터는 바디에 저장돼서 보내진다.

#### HTTP 응답

요청에 대한 결과를 반환하는 메시지

1. HTTP 응답은 HTTP ver, Status Code, Reason Phrase(처리 사유)로 구성된다.
2. 상태코드는 요청에 대한 처리 결과를 나타낸다. HTTP 표준인 RFC 2616은 대략 40여개의 상태 코드를 정의하고 있다.

| 상태 코드 | 설명 | 대표 예시 |
| --- | --- | --- |
| 1xx | 요청을 제대로 받았고, 처리가 진행 중임 | |
| 2xx | 요청이 제대로 처리됨 | • 200(OK): 성공 |
| 3xx | 요청을 처리하려면, 클라이언트가 추가 동작을 취해야 함 | • 302(Found): 다른 URL로 갈 것 |
| 4xx | 클라이언트가 잘못된 요청을 보내어 처리에 실패했다 | • 400(Bad Request): 요청이 문법에 맞지 않음<br>• 401(Unauthorized): 클라이언트가 요청한 리소스에 대한 인증이 실패함<br>• 403(Forbidden): 클라이언트가 리소스에 요청할 권한이 없음<br>• 404(Not Found): 리소스가 없음 |
| 5xx | 클라이언트의 요청은 유효하지만, 서버에 에러가 발생하여 처리에 실패했다 | • 500(Internal Server Error): 서버가 요청을 처리하다가 에러가 발생함<br>• 503(Service Unavailable): 서버가 과부하로 인해 요청을 처리할 수 없음 |

### HTTPS

## Web Browser

웹 브라우저는 서버와의 통신을 대신해주고 수신한 리소스를 시각화 해주는 클라이언트 도구

### URL(Uniform Resource Locator)

웹에 있는 리소스의 위치를 표현해주는 문자열

![](/assets/img/Xpert(4)/04.png)

| 요소 | 설명 |
| --- | --- |
| Scheme | 웹 서버와 어떤 프로토콜로 통신할지 나타낸다. |
| Host | Authority의 일부로, 접속할 웹 서버의 주소에 대한 정보를 가지고 있다. |
| Port | Authority의 일부로, 접속할 웹 서버의 포트에 대한 정보를 가지고 있다. |
| Path | 접근할 웹 서버의 리소스 경로로 `/`로 구분된다. |
| Query | 웹 서버에 전달하는 파라미터이며 URL에서 `?` 뒤에 위치한다. |
| Fragment | 메인 리소스에 존재하는 서브 리소스를 접근할 때 이를 식별하기 위한 정보를 담고 있다. `#` 문자 뒤에 위치한다. |

### Domain Name

Host는 Domain Name과 IP Address의 값을 가질 수 있다. IP 주소는 불규칙한 값이라 사람이 외우기 어려워 이를 Domain Name이 이름으로 치환해서 IP대신 사용한다.

DNS(Domain Name Server)는 Domain Name에 대해 질의하고 정보를 얻을 수 있는 서버이다.

`nslookup` 명령어를 이용해서 확인할 수 있다.

```bash
$ nslookup example.com
Server:		8.8.8.8
Address:	8.8.8.8#53

Non-authoritative answer:
Name:	example.com
Address: 93.184.216.34
```

## Cookie & Session

### Cookie

클라이언트의 IP주소와 User-Agent는 매번 변경될 수 있는 고유하지 않은 정보일 뿐 아니라, HTTP 프로토콜의 특징인 Connectionless와 Stateless 특징으로 서버가 클라이언트의 정보를 기억할 수 없다.

이러한 상태 정보를 유지하기 위해 Cookie가 생겼다.

1. 서버가 클라이언트에게 Key-Value로 이루어진 쿠키를 발급한다.
2. 클라이언트가 서버에 요청을 보낼 때 쿠키를 같이 보낸다.
3. 서버는 클라이언트의 쿠키를 확인해 클라이언트를 구분한다.

#### 쿠키 변조

악의적인 클라이언트가 다른 클라이언트의 쿠키를 변조해 접근할 수 있다.

### Session

인증 정보를 서버에 저장하고 해당 데이터에 접근할 수 있는 Key를 만들어 유저에게 전달하는 방식이다.

위에서 말한 쿠키 변조를 막기 위해서 사용된다.

쿠키 전달 간에 랜덤 문자열을 만들고 방문 횟수를 기록하는 식으로 운영된다.

## Same Origin Policy (SOP, 동일 출처 정책)

한 출처에서 로드된 스크립트가 다른 출처의 리소스에 접근하는 것을 막는 브라우저 보안 규칙이다.

`https://same-origin.com/` 이라는 오리진과 비교했을 경우는 다음과 같다.

| URL | 결과 | 이유 |
| --- | --- | --- |
| `https://same-origin.com/frame.html` | Same Origin | Path만 다름 |
| `http://same-origin.com/frame.html` | Cross Origin | Scheme이 다름 |
| `https://cross.same-origin.com/frame.html` | Cross Origin | Host가 다름 |
| `https://same-origin.com:1234/` | Cross Origin | Port가 다름 |

Origin은 프로토콜, 포트, 호스트로 구성되고 모두 일치해야 동일한 오리진이다.

> SOP는 `<img>`, `<script>`, `<style>` 는 막지 않는다.
{: .prompt-tip }

## Cross-Origin Resource Sharing (CORS, 교차 출처 리소스 공유)

SOP 때문에 막혀있는 교차 출처 접근을 서버가 허용해줄 수 있게 해주는 규칙이다.

1. 클라이언트가 A서버에서 페이지(JS 포함)를 받아 띄운다.
2. 그 JS가 B서버 데이터를 읽으려 시도한다.
3. 클라이언트가 B서버에 요청을 보낸다. → `Origin` 헤더가 자동 첨부되며 위조가 불가능하다.

```http
Origin: https://dreamhack.io
```

{:start="4"}
4. B서버가 클라이언트에 응답한다. → `Access-Control-Allow-Origin` 헤더를 담으면 그게 허락이다.

```http
Access-Control-Allow-Origin: https://dreamhack.io
```

{:start="5"}
5. 클라이언트가 그 값을 확인해 내 출처와 일치하면 JS에 데이터를 전달하고, 아니면 차단한다.

## JSON with Padding (JSONP)

CORS 이전에 사용하던 방식으로, `<script>` 태그를 막지 않는 것을 이용해서 SOP가 막는 데이터를 허용해준다.

callback 함수를 이용해서 응답을 함수 호출 코드로 감싸서 준다. 따라서 받는 입장에서는 자바스크립트 코드로 실행된다.

```html
<script src="https://api.example.com/data?callback=myCallback"></script>
```

```javascript
function myCallback(data) {
  console.log(data);
}
```
