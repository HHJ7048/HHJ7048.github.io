## Retrieval Augmented Generation

직역하면 검색 증강 생성, LLM을 실제 서비스에 적용하기 위한 필수 기술로, LLM이 학습하지 않았거나 알지 못하는 외부 정보를 검색(Retrieval)하고 생성에 활용하는 기술이다.

기업 내부의 비공개 데이터나 실시간 뉴스, 주식 정보와 같이 LLM이 학습을 통해서 얻기는 힘든 정보들을 사용하는 데에 도움을 준다.

### 작동 원리

#### 데이터 준비 단계

![데이터 준비 단계](</assets/img/2026-08-27-LLM공부(12)/01.png>)

1. Document Loader : 다양한 문서를 가져온다.
2. Text Splitter : 가져온 Data를 Chunk 단위로 쪼갠다.
3. Embedding : 데이터를 Vector 형태로 변환시킨다.
4. Vector Store : 임베딩 벡터를 빠르게 검색할 수 있는 Vector DB에 저장하고 Indexing한다.

#### Runtime 단계

![Runtime 단계](</assets/img/2026-08-27-LLM공부(12)/02.png>)

1. User의 입력에서 SysPrompt를 제외한 Query만 추출해서 RAG를 사용한다.
2. RAG는 저장된 Vector Store에서 필요한 정보(Enhanced Context)를 검색한다. 이때 검색 알고리즘으로는 대표적으로 HNSW, BM25(고전적인 방법), DPR 등을 사용한다.
3. SysPrompt, Query, Enhanced Context를 모델의 입력으로 넣는다.

이 전체 단계를 하나의 Pipeline으로 묶어서 자동화시킨다.

### 검색 알고리즘

1. **BM25**

   확률적 정보 검색 모델의 일종으로, 단어의 빈도와 문서 길이에 기반하여 문서의 점수를 계산한다. 특정 단어가 많이 발생할수록 해당 문서가 그 단어와 더 관련 있다고 판단한다.

2. **DPR**

   DPR은 딥러닝 기반 정보 검색 모델로, 문서와 쿼리를 임베딩하는 데 BERT 모델을 사용하고 임베딩 벡터끼리의 유사도를 계산해서 관련 문서를 검색한다.

3. **HNSW**

   kNN 방식을 위한 다층 그래프 자료구조로 만들어지고, 이웃 Query 중에 더 가까운 노드로 이동하며 가장 가까운 이웃을 찾는다.

### RAG의 필요성

기존의 LLM은 훈련 데이터에만 의존하기에 최신 정보나 특정 도메인의 깊은 정보에 대한 답변을 제공하는 데에는 한계가 있다. 또한 할루시네이션과 같이 부정확하거나 편향된 응답을 초래할 수 있다.

LLM과 RAG 기술을 융합하면 다음과 같은 장점을 가지고 있다.

1. 정보의 정확성 향상 : RAG는 질문에 답변을 하기 위해서 외부 지식을 검색할 수 있는 단계를 추가해준다.
2. 모든 정보를 모델이 포함하지 않아도 되기 때문에 크기와 효율성이 개선된다.
3. 복잡한 질문이나 긴 대화에서도 관련성 높은 정보를 제공한다.
4. 데이터 편향 문제를 완화시켜준다. RAG는 다양한 정보에 대해서 검색해서 알려주기 때문에 특정한 정보에만 편향된 답변을 생성하는 것을 억제시켜준다.

실제 LLM 모델은 웹 서칭과 같이 RAG와 비슷한 구조로 최신 정보를 받아오고 있다.

RAG는 회사 내부의 데이터나 국방부 기밀 정보와 같이 외부에 있는 정보를 LLM이 활용할 수 있도록 도와준다.

### 단점

1. 계속 Vector Store를 업데이트시켜줘야 한다. 만약 업데이트가 느려질 경우 최신 정보에 대한 답변을 제공하기 힘들어진다.
2. 검색 이후 답변을 생성하기에 연산 비용이 증가한다.

## Agentic RAG

기존의 RAG는 user의 입력을 검색하고 LLM의 입력으로 넣었다면, 이 방식은 LLM이 RAG를 Agent처럼 사용해 필요한 정보를 직접 RAG를 이용해 가져오는 방식이다.

### 기존 방식의 한계점 극복

1. 모든 입력에 대해 불필요한 검색을 강제한다.
   → 필요한 정보만 LLM이 직접 판단해서 검색한다.
2. 대명사와 같이 정확한 단어가 아닐 경우 검색에 실패할 수 있다.
   → LLM이 대명사와 같은 정보에 대한 내용은 스스로 검색어를 변경하면서 찾아낼 수 있다.
3. 여러 단계를 거쳐서 검색해야 필요한 정보를 구할 수 있다.

   ICAE 논문의 저자가 누구야 → ICAE가 뭔지 검색 → 논문의 저자를 검색
   → 기존 RAG와 달리 여러 턴에 거쳐 검색을 진행함으로써 더 구체적인 정보를 찾아낼 수 있다.

### 동작 원리

![Agentic RAG 동작 원리](</assets/img/2026-08-27-LLM공부(12)/03.png>)

1. Query Planning : 사용자의 입력을 쪼개서 어느 DB에 검색할지 계획을 수립한다.
2. Routing : 질문에 맞는 Tool을 선택한다. 여기서 내부 자료 검색이 필요한 경우 Vector Store를 선택한다.
3. Multi-hop Retrieval & Tool Use : 검색을 진행하고 정보가 부족할 경우 반복한다.
4. Self-Reflection / Evaluation

   검색된 문서가 질문과 정말 Relevance한지 검증한다.
   또한 할루시네이션이 없는지 직접 자가 검증한다.
   결과가 불합리하다면 검색 쿼리를 바꿔서 다시 검색을 진행한다.

### 단점

1. 판단 주체가 LLM이어서 오류가 생길 경우 증폭될 수 있다.
2. 보안적 취약성이 확장되어서 다양한 문제가 생길 수 있다.
3. 최종 답변만으로는 평가도 힘들고 관측도 불가능하다. 따라서 문제점을 찾거나 연산 시간을 예측하기가 힘들어진다.
