**아이디어** : 텍스트를 문자로 표현하면 2572의 size가 되고 sub-words로 표현하면 512의 컨텍스트 길이로 줄일 수 있다. 비슷한 방식으로 입력되는 토큰을 압축하면 추론 지연 시간과 GPU 메모리 측면에서 LLM 성능을 향상시킬 수 있지 않을까?

## ICAE 구조와 학습

ICAE는 인코더와 디코더 과정을 모두 수행한다.

![ICAE 전체 구조](</assets/img/논문리뷰(1)/01.png>)
_ICAE의 인코더-디코더 구조. 인코더는 원본 컨텍스트를 memory slots으로 압축하고, 디코더는 이를 바탕으로 텍스트를 복원한다._

### 사전 학습

#### 1. AE에 대한 사전학습

$$\mathcal{L}_{\text{AE}}(\Theta_{LoRA}) = -\sum_{i=1}^{L} \log P(c_i \mid \mathbf{m}_c,\, e^{[\text{AE}]},\, c_{<i};\, \Theta_{LLM},\, \Theta_{LoRA})$$

1. 인코더에서 기존 Context와 Memory tokens를 넣는다.
2. Memory slots으로 인코딩 시킨다. → 압축하는 과정
3. 메모리 슬롯을 바탕으로 텍스트를 생성한다.
4. 여기서 `[AE]`는 오토인코딩 사전학습을 나타내는 특수토큰이다.

입력 Context와 출력 Context 내용이 동일한지 확인할 경우, Memory slots이 제대로 Context 내용을 압축시키고 있는지 확인할 수 있다.

#### 2. LM에 대한 사전학습

$$\mathcal{L}_{\text{LM}}(\Theta_{LoRA}) = -\sum_{i=1}^{L} \log P(o_i \mid \mathbf{m}_c,\, e^{[\text{LM}]},\, o_{<i};\, \Theta_{LLM},\, \Theta_{LoRA})$$

AE만 진행한다면 단순 암기에 지나지 않을 수 있다. 우리가 원하는 목적인 LM 모델의 특성을 가져오려면 AE 학습 이후에 LM에 대한 학습도 이루어져야 한다.

> **Q.** AE와 LM에 대한 학습을 같이하게 되면 생성 시에 압축 토큰이 나올 수 있지 않을까?
>
> **A.** LM에 대한 학습을 충분히 하면 빈도가 줄어듦.
{: .prompt-tip }

### Instruction Fine-tuning

사전학습 이후 ICAE가 생성한 memory slot은 원본 Context를 잘 표현할 것으로 기대한다. 하지만 단순 암기, 이어쓰기의 목적이 아닌 다양한 프롬프트에 정확하고 적절하게 응답시키는 것을 목적으로 한다. 따라서 논문에서는 이러한 방식으로 Fine-tuning을 진행한다.

이 논문에서는 PWC(Context, Prompt, Answer)에 대한 샘플로 이루어진 240k의 데이터셋을 이용한다.

$$\mathcal{L}_{\text{FT}}(\Theta_{LoRA}) = -\sum_{i=1}^{\lvert r \rvert} \log P(r_i \mid \mathbf{m}_c,\, p,\, r_{<i};\, \Theta_{LLM},\, \Theta_{LoRA})$$

- **[인코더]** 원문 → LoRA-LLM → memory slot 생성
- **[디코더]** memory slot + 프롬프트(teacher-forcing 없이 그대로) + 응답(teacher-forcing) → LLM → 응답 생성 학습

#### LoRA(Low-Rank Adaptation) tuning

Full Fine-tuning과는 달리 원래 모델의 가중치를 업데이트 하는 것이 아니라, 모델의 기존 가중치 값 즉 기존 파라미터들은 그대로 두고 별도의 작은 크기의 행렬 두 개를 새롭게 모델에 추가하여 행렬 두 개만 학습하는 방식이다.

$$W = W_0 + \frac{\alpha}{r} BA$$

- 행렬 $B$는 $d \times r$의 크기
- 행렬 $A$는 $r \times k$의 크기
- $r$은 $A$, $B$의 크기를 선택하는 값
- $\alpha$는 추가 행렬의 영향력을 스케일링 해준다.

$r$을 선택해서 계산 비용(속도 / 메모리)과 표현력을 배분할 수 있다. 따라서 $r$ 값만 잘 조절한다면 Full Fine-tuning보다 더 작은 가중치만 학습해서 계산 속도가 빠르다.

참고자료 : [https://wikidocs.net/288626](https://wikidocs.net/288626)

> **Q.** LoRA에서 $r$이 커지면 학습시간은 길어지지만 더 정확하게 계산된다. 따라서 $r$이 커지면 $r$ 값에 따라서 $BA$의 변화율을 줄여줘야 하는 것이 아니라 늘려야 하는 거 아닌가?
>
> **A.** $r$이 커지면 그 안에 들어있는 원소들의 값이 커진다. (예: $r = 8 \rightarrow 64$ 일 경우 8배가 된다.) 하지만 $r$이 커진다고 해서 8배까지 반영하게 되어버리면 gradient가 발산해서 학습이 불안정해지기 때문에, $r$을 이용해 $BA$의 값을 늘리는 것이 아닌 줄여준다.
{: .prompt-tip }

**결론** : Context를 압축하는 $k$의 크기가 정확도에 큰 영향을 미치는 것을 확인할 수 있다. 4배를 초과할 경우($k = 128$일 때 Context length = 400~500 정도) 성능 하락이 시작되는 것을 확인할 수 있다.

![복원 실패 사례](</assets/img/논문리뷰(1)/04.png>)
_ICAE의 복원 오류 예시_

논문에서는 인간의 암기와 비슷한 실수를 한다고 나와 있다. 자신의 이해를 바탕으로 특정 부분은 선택적으로 강조하거나 무시하고, 또한 유사한 단어로 잘못 생성해내는 결과도 초래했다고 한다.

일반적인 텍스트보다 무작위 텍스트나 덜 일반적인 텍스트를 복원시키는 것이 정확도가 더 낮다고 한다. LLM의 성능에 따라서 암기 노력이 많이 줄어드는 것도 확인할 수 있다.

### 병렬 방식 ICAE

![병렬 방식 ICAE 성능](</assets/img/논문리뷰(1)/07.png>)
_여러 개의 memory slot을 연결한 병렬 방식의 성능_

**여러 개의 memory slot 연결**

- 2048개 memory slot이 4096 토큰 원본과 맞먹는 성능 → 약 20GB GPU 메모리 절약
- 4배까지 압축했음에도 빨간색 선과 파란색 선의 성능 차이가 크게 나지 않는 것을 볼 수 있음

## 시사점

1. **재귀 방식(AutoCompressor)의 한계** : 청크 2를 압축할 때 압축된 청크 1을 같이 넣어서 처리하는 방식으로, 아무리 GPU가 많아도 병렬처리가 불가능하다는 단점이 있다.
2. 재귀 구조는 역전파에서도 여러 단계를 거쳐야 해서 기울기가 불안정해질 수 있는 문제가 있다.
3. 병렬 방식에서는 앞의 청크 내용을 뒤의 청크가 몰라서 중복되는 내용을 놓칠 위험이 있다. (예: 앞에서 언급한 사람이 뒤에서 나올 때)
4. 따라서 이 논문에서는 **실용성과 성능 사이의 균형점을 어디서 찾을 것인가**에 대한 질문을 던진다.

## 추가 조사 내용

실제로 현재 상용화되는 LLM 모델들은 연산량 소모를 줄이기 위해 어떤 방식을 사용하고 있는가?

### 모델 구조

1. **Mixture-of-Experts (MoE)**

   여러 개의 전문화된 서브모델(expert)과 라우팅을 담당하는 게이팅 네트워크로 구성되며, 추론 시에는 파라미터의 일부만 활성화되어 토큰 메모리 사용량을 줄인다.

2. **양자화**

   FP16에서 INT8이나 INT4로 낮추면 메모리는 2~4배 줄고 추론 비용은 약 50% 절감되며, 원래 정확도의 95~99%를 유지한다.

### 추론 단계

1. **KV 캐시 최적화**

   자주 나오는 프롬프트를 캐시화 시켜서 비슷한 문맥이 반복될 경우 더 효율적으로 처리한다. PagedAttention과 prefix caching을 활성화하면 처리량이 2~4배 증가한다.

2. **Speculative Decoding (추측 디코딩)**

   작고 빠른 draft 모델이 여러 토큰을 먼저 제안하면, 크고 정확한 target 모델이 이를 한 번의 병렬 패스로 검증한다. 결과물은 일반적인 자기회귀 디코딩과 수학적으로 동일하다. 기성 draft 모델로도 2~3배 속도 향상이 나오고, 최적화된 구현은 5배까지 도달한다.

3. **연속 배칭(Continuous Batching)**

   vLLM과 TGI 같은 서빙 프레임워크에 기본 내장되어 있다.
